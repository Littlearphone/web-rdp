# 2K 高分屏：提帧率 / 降延迟 实测报告（含方法学修正）

测量环境：**RTX 3070 + 3440×1440 @ 180Hz**，编码后端 `NVIDIA H.264 Encoder MFT`（硬件异步 MF）。

---

## 0. 先纠正上一版报告的错误结论

上一版报告写的「2K 帧率 +36%、E2E 延迟 -41%」**是基于无效测量得出的，予以撤回**。

原因是我写的"高刷新率画面变化发生器"（`Motion2`）有 bug：它用 `Application.Idle` 驱动重绘，
而 Idle **只在消息队列变空时触发一次**；循环里 `break` 之后不会再被唤醒，必须靠外部消息
（鼠标移动）才能继续。表现为**"鼠标移上去才变化"**，实际上几乎没有在制造画面变化。

后果：所谓"变化源"其实主要来自我自己的终端输出，测到的 ~40fps 是被这个噪声源卡住的，
不是管线能力。所以：

- 60Hz 与 120Hz 目标测出来一模一样（发生器没在工作）
- 各档位、各版本的 fps 都挤在 40 上下，版本差异被当成"优化收益"
- 对照实验的结论全部不可信

第二版发生器（`Motion3`）同样有问题：泵线程在构造函数里就启动，此时窗口句柄还没创建，
`BeginInvoke` 直接抛异常、循环立刻退出（表现为"一点变化都没有"）。已改为
`OnHandleCreated` 之后再启泵，并把达成速率写文件自报。

### 现在的验证方式（三道独立确认）

1. **发生器自报**：`Motion3` 每 10 秒把"实际重绘次数 / 用时"写入日志
   → 实测 **114–119 Hz**（目标 120）
2. **独立采集探针**：`backend/tools/capprobe` 只做 DXGI 采集、统计真正拿到多少"已变化"帧
   → 空桌面 **1–30 Hz**（背景噪声）；发生器开启后 **105.4 Hz**
3. **A/B 时确认发生器存活**：每次测量前打印自报速率

工具：`backend/tools/capprobe`、`backend/tools/e2ebench`。

## 1. 真正卡住 60fps 的原因：帧率节流算法（不是编码、不是转换）

现象：fps 与档位**无关**（3440×1440 与 1920×804 都是 ~50fps），
单帧最大间隔 `enc_ms` 稳定 ~28ms —— 说明瓶颈与"每帧要做多少像素处理"无关。

根因在 `native_session.go` 的档位帧率节流：

```go
target := time.Second / time.Duration(s.fps)   // 60fps → 16.67ms
if d := time.Since(lastEncode); d < target { continue }   // ← 问题在这
```

这是"距上一帧够不够久"的判据：

- 源帧率 **高于**目标时稳定**砍半**：105Hz 源 → 只能编到 ~52fps
- 源帧率**恰好等于**目标时，抖动会让它间歇性砍半：60Hz 源 → 30~60fps 摆动

改成**配额累计**（token bucket）：每收到一帧把时间增量存进 `credit`，攒够一帧才编码、
并扣掉一个配额；长期稳定在目标帧率，且静止/卡顿后不补爆发（`credit` 上限 2×target）。

### 实测（验证过的发生器，各 2 轮）

| 档位 | 基线 586c559 | 配额节流后 | 变化 |
|---|---|---|---|
| maxw=0（原始 3440×1440） | 49.7 / 49.8 fps | **60.0 / 60.0 fps** | **+20%** |
| maxw=2560 | 48.8 / 50.6 fps | **60.0 / 60.1 fps** | +20% |
| maxw=1920 | 49.5 / 50.2 fps | 60.0 fps | +20% |
| 单帧最大间隔 `enc_ms` | 28–33ms（偶发 109ms） | **24–28ms** | 抖动更小 |

> 注：60fps 是档位目标上限（`fps=0`(自动) 时 `newNativeSession` 取 60）。
> 所以修好节流后是"稳定顶到上限"，而不是无限提升。

## 2. 我确实引入过的一个退化（已修复）

第一版融合内核把缩放与色彩转换合并成一趟，但内层循环是：

```go
sx := x * sw / tw      // 每像素一次整数除法，编译期无法消除
```

**不缩放时（原始分辨率档位）这个除法本该被消掉**，却仍然每像素执行一次：
3440×1440 每帧多出约 **740 万次整数除法**；而原来的 `BGRAToNV12` 是纯线性扫描。
我还主动删掉了等尺寸捷径，等于亲手把最常用的"原始分辨率"路径改慢（实测 42.4 → 40.5 fps）。

修复：
- **等尺寸走专用无除法线性内核** `pureNV12Range`（并可并行）
- 需要缩放时**每帧只建一次索引表** `nv12Index`（`x*sw/tw` 只算 tw 次而非 tw×th 次），内层只查表

### 内核实测（真实采集帧，输出均与旧实现**逐字节一致**）

| 内核 | 等尺寸(原始分辨率) | 缩放至 2560×1070 |
|---|---|---|
| 旧实现 | 9.49 ms | 12.65 ms |
| 新融合 串行 | 9.87 ms | 6.84 ms |
| **新融合 并行** | **2.50 ms** | **2.25 ms** |

并发度实测：在 60fps 上限下 **1 / 4 / 8 线程没有区别**（都是 60.0fps、~25ms），
因为该阶段已不在关键路径上。因此默认值改为保守的 `NumCPU/4`（上限 4），
并支持环境变量 `WEBRDP_CVT_WORKERS=1|N` 覆盖以便日后调优。

采集侧也顺手去掉了重复拷贝：`readbackTexture` 直接产出最终缓冲，
不再由 `AcquireBGRA` 做第二次 19.8MB 全量拷贝。

## 3. 当前状态与下一步

| 项 | 现状 |
|---|---|
| 2K 档位帧率 | **稳定 60.0 fps**（= 档位上限） |
| 单帧最大间隔 | ~25ms（原 28–33ms，偶发 109ms） |
| 转换内核 | 2.25–2.50 ms，逐字节兼容旧实现 |
| 采集回读 | 单次拷贝（原两次） |
| 无 N 卡回退 | 未使用任何厂商专有 API，A/I 卡一致；三级编码回退链不变 |

**想突破 60fps 的话**（显示器 180Hz、按像素率钳制上限约 141fps @3440×1440），
下一个杠杆是：把"自动"档位从固定 60 改为**跟随显示器刷新率**（并受像素率上限约束）。
这会让 2K 跑 120fps 级别，但带宽/CPU 也会随之上升 —— 属于产品取舍，需要你确认。

未验证：多显示器/混合 DPI、WebRTC 端到端主观延迟（本次全部是服务端 WS 路径的客观指标）。
